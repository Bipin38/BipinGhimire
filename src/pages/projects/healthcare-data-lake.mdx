## Context

Hanker LLC’s clinical and operational data lived in a NextGen EHR database on SQL Server, behind a VPN. I designed and built a data lake on AWS from the ground up to centralize that data for analytics, automated reports, and downstream data engineering.

## How it works

### Short-lived compute for a private source

The source database sits behind a VPN, so ingestion runs on an EC2 instance that Lambda starts for each daily run. The instance establishes the VPN connection, executes the synchronization workloads, and shuts down when they finish.

### Full and incremental loads

The pipeline supports full loads and incremental synchronization. Incremental runs use hash-based change detection to identify inserted and modified records.

### Storage laid out for history

Data lands in S3 as Parquet in daily partitions, which supports historical processing and efficient downstream analysis. Glue Crawlers discover the ingested datasets and register their schemas in the Glue Data Catalog.

### From raw tables to Gold

Glue PySpark transformations clean, join, and aggregate the source tables and calculate healthcare business metrics. The output is a set of analytics-ready Gold tables, exposed through the Data Catalog and queried with Athena.

### Operability

Every run includes data validation, pipeline logging, and error handling. The platform’s AWS resources are provisioned with CloudFormation templates.

## Results

- About **10 million records** ingested or updated daily across **100+ source tables**.
- Analysts and other data engineers build and automate dashboards on the centralized data.

## Scope

Dashboard-level performance gains weren’t measured separately, so none are claimed here.
